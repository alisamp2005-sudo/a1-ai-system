# RAG Пайплайн (База знаний)

Retrieval-Augmented Generation (RAG) используется Агентом-Юристом и Агентом-Аналитиком для ответов на основе корпоративных документов, договоров и СНиПов.

## Архитектура RAG

1. **Источник данных:** Сетевая папка (SMB/NFS) со сканами договоров (PDF, JPG) и регламентами.
2. **Watchdog:** Python-скрипт мониторит папку. При появлении нового файла запускает обработку.
3. **OCR (Оптическое распознавание):** Если файл — скан, используется Tesseract OCR (или Marker) для извлечения текста.
4. **Чанкование (Chunking):** Текст разбивается на смысловые куски (chunks) по 500-1000 токенов с перекрытием (overlap) в 100 токенов для сохранения контекста.
5. **Векторизация (Embedding):** Модель `nomic-embed-text` (запущена через Ollama) превращает текст в числовые векторы.
6. **Хранение:** Векторы и метаданные (имя файла, дата, тип) сохраняются в ChromaDB.

## Процесс поиска (Retrieval)

1. Пользователь задает вопрос (например, "Какой штраф за просрочку по договору с ООО 'Ромашка'?").
2. Вопрос векторизуется той же моделью `nomic-embed-text`.
3. ChromaDB выполняет семантический поиск (Cosine Similarity) и возвращает топ-5 наиболее релевантных чанков.
4. Эти чанки подставляются в системный промпт LLM (Qwen 32B) как `<context>`.
5. LLM генерирует ответ, опираясь ТОЛЬКО на предоставленный контекст.

## Структура метаданных в ChromaDB

При сохранении чанка в ChromaDB обязательно передаются метаданные:
```json
{
  "source": "contract_romashka_2025.pdf",
  "doc_type": "contract",
  "project_id": "uuid-1234",
  "date": "2025-04-10",
  "page": 12
}
```
Это позволяет делать гибридный поиск: "Найти семантически похожий текст, НО только в документах с `doc_type = contract` и `project_id = uuid-1234`".
