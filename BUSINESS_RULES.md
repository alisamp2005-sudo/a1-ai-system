# Бизнес-правила и архитектурные решения MVP

Данный документ фиксирует все утвержденные решения по ключевым точкам логики системы. Все пункты согласованы с заказчиком и являются обязательными для реализации. Документ является единственным источником истины при возникновении разночтений между другими файлами проекта.

---

## 1. Приоритет назначения исполнителя

При создании задачи система последовательно проверяет правила назначения. Первое сработавшее правило определяет исполнителя.

| Приоритет | Условие | Исполнитель |
|:---------:|---------|-------------|
| 1 | Найдено правило в матрице `тип + конкретный объект` | Исполнитель из записи матрицы |
| 2 | Найдено правило `тип + отдел` | Ответственный сотрудник или руководитель отдела |
| 3 | Тип определен, но правила назначения нет | Руководитель соответствующего отдела |
| 4 | После двух уточнений не определены тип или объект | Зиновьева А. (Исполнительный директор) |

Конфликт между "назначением руководителю отдела" и "автоматическим назначением по матрице" устранен: **матрица имеет приоритет**. Руководитель отдела получает задачу только если матрица не содержит конкретного правила.

---

## 2. Справочник типов задач (Task Types)

Router обязан классифицировать каждый запрос строго в один из следующих типов. Произвольные значения недопустимы.

| Тип (`task_type`) | Отдел-владелец | Без объекта? | Приоритет по умолчанию |
|-------------------|---------------|:------------:|:----------------------:|
| `safety` | Служба ТБ (Поляков С.Б.) | Нет | P1 |
| `procurement` | Снабжение | Нет | P2 |
| `hr` | HR | Да | P2 |
| `finance` | Финансы | Да | P2 |
| `legal` | Юридический | Да | P2 |
| `project_management` | Производство (РП) | Нет | P2 |
| `reporting` | Производство (Прорабы) | Нет | P3 |
| `general` | Общее (Зиновьева А.) | Да | P3 |

Router возвращает строго валидируемый JSON: `task_type`, `priority`, `project_candidate`, `confidence`, `needs_clarification`, `clarification_options`.

---

## 3. Привязка задачи к объекту

Система использует гибридный подход из четырех шагов:

| Шаг | Условие | Действие |
|:---:|---------|----------|
| 1 | Router извлек название объекта из текста | Привязывает автоматически |
| 2 | Не удалось, но пользователь привязан к одному объекту | Назначает объект по умолчанию |
| 3 | Пользователь привязан к нескольким объектам | Бот спрашивает: "Уточните объект: [список кнопок]" |
| 4 | Общекорпоративный вопрос (HR, финансы) или тип допускает отсутствие объекта | Задача без объекта допускается |

---

## 4. Статусы задач и таблица переходов

В MVP реализуются 5 статусов с жесткой таблицей разрешенных переходов:

| Откуда | Куда | Кто может | Обязательные данные |
|--------|------|-----------|---------------------|
| — | `new` | Система | Тип, приоритет, источник, срок, получатель |
| `new` | `in_progress` | Исполнитель | Подтверждение принятия |
| `new`, `in_progress` | `paused` | Руководитель, топ-менеджмент | Причина, дата/условие возобновления |
| `paused` | `in_progress` | Тот, кто поставил на паузу, либо более высокая роль | Причина возобновления |
| `new`, `in_progress`, `paused` | `done` | Исполнитель, руководитель, администратор | Результат или комментарий закрытия |
| `new`, `in_progress`, `paused` | `cancelled` | Руководитель, топ-менеджмент | Обязательная причина отмены |

Любой другой переход запрещен. Нажатие устаревшей inline-кнопки (если задача уже изменена) отклоняется с сообщением: "Задача уже обновлена. Текущий статус: [статус]."

## 5. Получатель эскалации на уровне 100% SLA

Владельцем задачи является **отдел**. РП объекта получает информационную копию уведомления.

| Тип задачи | Получатель 100% SLA | Копия |
|------------|---------------------|-------|
| Задача по конкретному объекту (без отдела) | РП объекта (`projects.manager_id`) | — |
| Задача по отделу + объект | Руководитель отдела (`departments.head_id`) | РП объекта |
| Задача по отделу (без объекта) | Руководитель отдела | — |
| Общая задача | Зиновьева А. | — |

**Правило недублирования:** если получатель эскалации совпадает с текущим исполнителем, уведомление пропускается и система переходит к следующему уровню эскалации.

## 6. Изменение параметров задачи после создания

Изменение исполнителя, приоритета и дедлайна разрешено после создания задачи.

**Матрица прав на изменение:**

| Роль | Может менять |
|------|-------------|
| ГД (Алимов З.Т.), Зиновьева А., Лыков М.А. | Всё |
| Администратор | Всё |
| Руководитель отдела | Задачи своего отдела |
| Исполнитель | Ничего (может только закрыть или запросить продление) |

**Правила пересчета SLA:**

| Изменение | Поведение SLA |
|-----------|---------------|
| Смена исполнителя | SLA перезапускается с нуля, `sla_version` увеличивается |
| Смена приоритета | SLA пересчитывается по новому приоритету от текущего момента |
| Смена дедлайна | SLA привязывается к новому дедлайну |

При любом изменении старые контрольные точки аннулируются, создаются новые. Журнал уведомлений использует ключ `task_id + threshold + sla_version` для дедупликации.

## 7. Обработка голосовых сообщений

Расшифровка (Whisper) направляется в Router **без подтверждения пользователем**. Whisper Large v3 дает точность ~95%+ на русском. Если Router не уверен в содержании, он задает уточняющий вопрос. Опционально: команда `/transcript` показывает последнюю расшифровку.

## 8. Поведение при низкой уверенности Router

| Ситуация | Действие |
|----------|----------|
| Router выставил `needs_clarification = true` | Бот спрашивает: "Уточните, это касается [вариант А] или [вариант Б]?" |
| Не определен объект (а тип требует объекта) | Бот спрашивает: "По какому объекту?" (кнопки) |
| Не определен исполнитель | Назначается по матрице (раздел 1) |
| После 2 уточнений всё ещё неясно | Задача создается в статусе `new` и уходит Зиновьевой А. с историей диалога |

## 9. Конфиденциальность (утвержденная формулировка)

> LLM, Whisper, Vision, обработка документов и базы данных размещаются в локальном контуре компании. Документы, аудио и содержимое запросов не направляются внешним AI-провайдерам (OpenAI, Anthropic, Google и др.). Telegram используется как внешний транспортный канал: сообщения боту передаются через инфраструктуру Telegram и не относятся к сквозно зашифрованным Secret Chats. Через Telegram не допускается передача документов или сведений, отнесённых компанией к категориям, запрещённым для внешних мессенджеров.

**Что запрещено передавать через Telegram:**

| Категория | Через TG? | Альтернатива |
|-----------|:---------:|-------------|
| Текстовые запросы, команды | Да | — |
| Голосовые сообщения (поручения) | Да | — |
| Фото с объектов (отчеты, ТБ) | Да | — |
| Уведомления и напоминания | Да | — |
| **Полные тексты договоров** | **Нет** | Mini App или ссылка на NAS |
| **Финансовые отчеты (P&L, бюджеты)** | **Нет** | Веб-дашборд |
| **Персональные данные сотрудников** | **Нет** | Админка |

## 10. SLA: рабочее время и исключения

| Параметр | Значение |
|----------|----------|
| Часовой пояс | `Europe/Moscow` (UTC+3) |
| Рабочий день | 09:00–18:00 |
| Рабочие дни | Пн–Пт |
| Праздники | Производственный календарь РФ (справочник, обновляется ежегодно) |
| Единый для всех | Да, единый график для всех отделов и объектов |
| **P0 (Критический)** | **Исключение: 24/7 контроль, без учета выходных и праздников** |
| Задача, созданная после 18:00 (P1-P3) | Отсчет SLA начинается с 09:00 следующего рабочего дня |
| Пауза | Хранится `remaining_sla_seconds`, а не дата дедлайна |

## 11. Механизм "Запросить продление"

| Параметр | Правило |
|----------|---------|
| Кто может запросить | Исполнитель (кнопка "Запросить продление") |
| Кто согласует | Руководитель отдела (или РП объекта, если задача по объекту) |
| Максимальное продление | +50% от исходного SLA (однократно) |
| Если согласовано | SLA пересчитывается, `sla_version` увеличивается, старые контрольные точки аннулируются |
| Если отклонено | Исходный SLA остается, исполнитель получает "Продление отклонено" |
| Фиксация | Запись в `task_events`: кто запросил, кто решил, новый срок |

## 12. Информационные сообщения (не задачи)

В MVP, если Router определяет сообщение как информационный запрос (не требующий действия от человека), бот отвечает: "Этот вопрос будет обработан после подключения профильного агента. Сейчас я могу помочь с постановкой задач и контролем сроков." Задача **не создается**. В Фазе 2 такие запросы обрабатываются Агентом-Аналитиком.

## 13. Ручное создание задач

В MVP ручное создание задач **допускается**. Право имеют: ГД, Зиновьева А., Лыков М.А., руководители отделов. Реализуется через команду `/newtask` или кнопку в боте. Бот последовательно запрашивает: тип, объект, исполнителя, описание. Приоритет и дедлайн подставляются по умолчанию из матрицы, но могут быть переопределены.

## 14. Механизм SLA (техническая реализация)

Вместо шести отложенных Celery-задач с ETA используется **надежная модель на базе PostgreSQL**:

1. При создании задачи в таблицу `sla_checkpoints` записываются 6 строк (50%, 80%, 100%, +24ч, +48ч, +72ч) с полями `next_check_at`, `threshold`, `is_processed`, `sla_version`.
2. Celery Beat запускает периодическую задачу **каждую минуту**.
3. Задача выбирает из `sla_checkpoints` все строки, где `next_check_at <= now()` и `is_processed = false`, с блокировкой строк (`SELECT ... FOR UPDATE SKIP LOCKED`).
4. Для каждой наступившей контрольной точки отправляется уведомление и записывается в `notification_log` с ключом `task_id + threshold + sla_version`.
5. При паузе, переназначении или изменении дедлайна — старые контрольные точки помечаются `is_processed = true`, создаются новые с увеличенным `sla_version`.

Это гарантирует: восстановление после перезапуска, отсутствие дублей, корректный пересчет при паузах.

## 15. Идемпотентность входящих сообщений

Каждое входящее сообщение Telegram имеет уникальный `update_id`. Система хранит обработанные `update_id` и отклоняет повторные. Это предотвращает создание дублирующих задач при повторной доставке webhook.

## 16. Расширенная модель данных MVP

Минимально необходимые таблицы для реализации утвержденных правил:

| Таблица | Назначение |
|---------|-----------|
| `users` | Пользователи (telegram_id, role, phone E.164) |
| `departments` | Отделы (name, head_id) |
| `user_departments` | Принадлежность сотрудника к отделам |
| `projects` | Строительные объекты (name, manager_id) |
| `user_projects` | Привязка пользователя к объектам (is_default) |
| `routing_rules` | Матрица назначения (task_type, project_id, department_id, default_assignee_id, default_priority) |
| `tasks` | Задачи (все поля включая sla_version, remaining_sla_seconds, sla_due_at, creator_id, department_id, task_type, source) |
| `task_events` | Неизменяемая история всех действий над задачей |
| `sla_checkpoints` | Контрольные точки SLA (next_check_at, threshold, is_processed, sla_version) |
| `notification_log` | Журнал уведомлений (дедупликация, ретраи) |
| `work_calendar` | Производственный календарь РФ (дата, is_workday) |

Авторизация: принимается только контакт, подтвержденный Telegram как контакт самого отправителя (не пересланный).

## 17. Крайние случаи и уточнения SLA

Данный раздел фиксирует точечные правила реализации, устраняющие последние неоднозначности.

### 17.1. Поведение SLA при паузе и возобновлении

При переводе задачи в статус `paused`:
- Уже обработанные контрольные точки (`is_processed = true`) **не затрагиваются** и не повторяются после возобновления.
- Ещё не наступившие контрольные точки **сдвигаются** на время паузы (разница между `paused_at` и моментом возобновления, с учетом рабочего календаря).
- `sla_version` **не увеличивается** при паузе/возобновлении. Увеличение версии происходит только при смене исполнителя или дедлайна.

Пример: задача с SLA 24 рабочих часа. Отправлено 50%-напоминание (12ч). Задача поставлена на паузу. После возобновления 50%-напоминание не повторяется; оставшиеся точки (80%, 100%, +24ч, +48ч, +72ч) сдвигаются на длительность паузы.

### 17.2. Исчисление +24/+48/+72 часов после просрочки

| Приоритет | Основной SLA | +24ч / +48ч / +72ч после просрочки |
|:---------:|:------------:|:-----------------------------------:|
| **P0** | Календарные часы 24/7 | **Календарные часы 24/7** |
| **P1** | Рабочие часы | **Рабочие часы** |
| **P2** | Рабочие часы | **Рабочие часы** |
| **P3** | Рабочие часы | **Рабочие часы** |

Для P1–P3 "+24 рабочих часа" означает: 24 часа, отсчитанные только в интервале 09:00–18:00 по рабочим дням (9 рабочих часов в сутки). То есть +24 рабочих часа ≈ 2 рабочих дня и 6 часов.

### 17.3. Fallback при совпадении получателя эскалации с исполнителем

Если получатель очередной эскалации совпадает с текущим исполнителем задачи, уведомление направляется следующему лицу по фиксированной цепочке:

| Ситуация | Следующий адресат |
|----------|-------------------|
| Исполнитель = РП объекта или руководитель отдела | **Зиновьева А.** |
| Исполнитель = Зиновьева А. | **Лыков М.А.** |
| Исполнитель = Лыков М.А. | **Алимов З.Т.** |
| Исполнитель = Алимов З.Т. | Эскалация невозможна (финальный уровень) |

### 17.4. Объект из текста не найден в справочнике

Если Router извлек из сообщения название объекта, но точного совпадения в справочнике `projects` нет:

1. Система выполняет нечеткий поиск (fuzzy match) и показывает до 5 ближайших вариантов в виде кнопок.
2. Добавляется кнопка "Другой объект" (для ручного ввода или отсутствия привязки).
3. Задача **не создается** до подтверждения пользователем.
4. Если пользователь не отвечает в течение 10 минут — запрос сохраняется в очереди и бот повторяет вопрос при следующем сообщении пользователя.

### 17.5. Ограничения выбора исполнителя при `/newtask`

| Роль создателя | Кого может назначить исполнителем |
|----------------|-----------------------------------|
| ГД (Алимов З.Т.), Зиновьева А., Лыков М.А. | Любого сотрудника из справочника `users` |
| Руководитель отдела | Только сотрудников своего отдела (`user_departments`) или сотрудников, привязанных к его объектам (`user_projects`) |
| Администратор | Любого сотрудника |

При попытке назначить сотрудника вне зоны ответственности бот отклоняет действие: "У вас нет прав назначать задачи этому сотруднику."
